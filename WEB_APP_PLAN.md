# Web App Plan: a Go front end for the music pipeline

A browser app, written in Go, for running the music pipeline. You upload a
WAV (a Bluebox mix), pick the music type, choose which processing steps to
run (only the ones that make sense for that type), choose the output
formats, and download the results. Prepared 2026-10-05.

## Principles

- **The Python scripts stay the source of truth.** Go never rebuilds an
  ffmpeg chain or duplicates recipe logic. It validates the form, turns it
  into a CLI call to the existing scripts, runs that call, streams progress,
  and serves the files. Anything the web app does, you can also do from the
  terminal with the same flags.
- **Options come from `music_recipes.json`**, not from a list hard-coded in
  Go. A new genre or a changed default in the recipes appears in the UI
  without touching Go.
- **The app is one binary.** Templates, CSS, and JS are built into the
  binary with `go:embed`. There's no Node toolchain and no build step for
  the front end. The only runtime needs are `python3`, `ffmpeg`, and the
  Python dependencies the scripts already use.
- **It's local and single-user first.** It listens on `127.0.0.1` by
  default. Making it reachable on your network is an explicit flag, and
  that flag requires a token.
- **The repo's existing rules carry over:**
  - nothing is guessed, so the music type is a required choice
  - the source file is never modified
  - there's a "show plan" button (`--plan-only`) before every render
  - every job keeps its `REPORT.txt`

## Decisions (2026-10-05)

- **All three pipelines:** music, nature, and speech. The pipeline is
  the first choice on the page; its types follow (music genre, nature
  label; speech has none).
- **FLAC and MP3 are in**, alongside WAV 24-bit and WAV 16-bit.
- **Advanced is collapsed by default.** Every option is marked basic or
  advanced in the capabilities document.
- **Still open:** localhost only, or reachable on your network? Until
  answered, the server binds to `127.0.0.1`.

## Phase 1 (done): the Python interface

Built on `feature/web-app`. Every change is opt-in, so existing command
lines produce exactly what they did before (checked by a test).

| Piece | What it gives the web app |
|---|---|
| `pipeline_capabilities.py` | One JSON document for all three pipelines. It covers types with summaries; every option with its kind, Basic/Advanced, per-type defaults, range, the flag it maps to, and which type/output/other option it depends on; outputs; formats; and dependency gating (e.g. the noise-profile options are disabled with an install hint while `noisereduce` is missing). It also contains `build_argv()`, the reference mapping from form values to a command line, which the Go port must match. |
| `pipeline_io.py` | Shared `--formats` (wav24, wav16, flac, mp3, all encoded from the 24-bit master and tagged) and `--progress-json`. Progress is `@@progress {...}` lines on stdout: a `plan` first, then `step_start` / `progress` / `step_end` / `step_error`, and a `manifest` of deliverables last. Child processes tag their events with `parent`. |
| `process_music_wav.py` | Per-step switches (`--no-eq`, `--no-dynamic-eq`, `--no-glue`, `--mono-bass-hz`, `--highpass-hz`, `--softclip`/`--softclip-threshold`, `--fade-in`/`--fade-out`), `--formats`, `--plan-only --json`, progress |
| `release.py` | `--outputs` (master, clip, video_16x9, video_9x16, video_1x1, captions, analysis); runs only the steps those outputs need. Passes the mastering switches through, adds `--emoji`/`--no-emoji`/`--symmetry`, `--formats`, `--plan-only --json`, and progress with a final manifest. |
| `process_field_wav.py`, `process_speech_wav.py` | `--formats`, `--title`/`--artist` tags, `--plan-only --json`, progress + manifest. Nature outputs map to `--skip-long` / `--skip-short`. |
| `visualize_wav.py` | Progress events with frames done out of total |
| `audio_peaks.py` | A waveform overview (min/max pairs) for any file, streamed through ffmpeg, so a 45-minute jam stays cheap |
| `tests/` | `pytest tests/`. 66 contract tests (every option's flag is accepted by its real script, JSON plans parse, bad input is rejected) plus 4 render tests (formats, loudness, events, manifests, unchanged defaults). The synthetic tracks are generated by `tests/make_test_tracks.py`. |

Names changed from the first draft of this plan: `music_capabilities.py`
became `pipeline_capabilities.py` (it covers all three pipelines), and
the waveform comes from `audio_peaks.py` rather than from the music
analysis.

## Phase 2 (done): the Go server

`web/` (see `web/README.md`). The server is standard library only, one
binary, and loopback-only until phase 5. It covers:
- **Capabilities:** cached, and reloaded when a recipe file changes.
- **Command lines:** the argv builder is a port of the Python one. A test
  runs 675 generated cases through both and requires 663 identical command
  lines and 12 agreed rejections.
- **Uploads:** streamed to disk, checked by RIFF/WAVE header, probed with
  ffprobe, mono/stereo only.
- **Waveform and analysis:** peaks and analysis endpoints, both cached.
- **Plans:** `--plan-only --json` previews.
- **Jobs:** a queue with job state persisted to disk (jobs survive a
  restart, and unfinished ones are marked "interrupted").
- **Live progress:** server-sent events with step progress (including
  video frames) and log lines.
- **Cancel:** process-group cancel; a test checks that a canceled video
  render leaves no processes behind.
- **Downloads:** files served only from the job's own manifest, after a
  symlink-safe check that they live inside the job folder. Range requests
  work for in-page players, and there's a zip of everything.
- **Security:** CSP and other security headers, plus a same-origin check
  and a custom header on every state-changing request.

## Phase 3 (done): the browser interface

Implemented in `web/ui/static` (`index.html`, `app.css` ~400 lines,
`app.js` ~800 lines), embedded into the binary. It follows the screens
described below, with these choices:
- Dark studio theme by default, with light following the OS or the toggle.
  The gold-to-violet accent matches the videos.
- No inline styles or scripts, so the strict CSP holds.
- Every option renders from the capabilities, with its per-type default.
  Advanced starts collapsed. Unset numbers show a "Customize" button
  rather than a misleading slider position.
- The title defaults to the uploaded file's name. Without this it would
  become "input", because every upload is stored as input.wav.
- Live job view over SSE, with players and downloads for results, and
  "Edit & run again".

Tested in the browser pane, at desktop and phone width (no horizontal
scroll at 375px), in light and dark:
- upload → techno analysis (127.9 BPM, drop at 0:15) → Advanced changes
  → plan → run (frame progress) → results
- re-run as speech, with the file-name title
- the jobs drawer

## What the user sees

Five steps in a single page. Each step unlocks the next. First, pick
the **pipeline**: Music, Nature, or Speech. The rest adapts to it; speech
skips the type step.

1. **Upload.** Drag and drop a WAV (or pick one).
   - The browser shows upload progress.
   - The server checks the RIFF/WAVE header, then runs `ffprobe` and shows
     length, sample rate, bit depth, and channels.
   - A wrong format or a multichannel file is rejected with a clear message.
2. **Music type.** One card per genre: ambient, trap, techno, psytrance.
   - Each card shows the tempo range, the default visual style, and an
     "untested recipe" badge.
   - Picking one starts `music_analyze.py` right away (about 10 seconds).
     Some options depend on the file itself, not just the genre: a beatless
     ambient track can't make a bar-exact loop, so loop mode is disabled
     with the reason shown.
   - **Analysis panel:**
     - BPM (trap shown at ~70), key with Camelot, loudness, true peak
     - the analyzer's flags, e.g. "bass will vanish on a phone"
     - a waveform with color bands for the sections and a marker on the
       main drop
3. **Options.** Grouped panels. Each option shows its genre default, and
   options that don't apply to this genre or file are hidden or disabled
   with a one-line reason.
   - **Trim:** start and end. You can set them by dragging handles on the
     waveform.
   - **Loudness:** preset (YouTube / Instagram / custom LUFS and true
     peak). Ambient shows its built-in −2 LU offset.
   - **Processing steps** (each a toggle with its setting):
     - subsonic high-pass (Hz)
     - mono bass (crossover Hz)
     - stereo width, applied above the crossover only
     - tonal EQ (the recipe's curve, shown read-only in plain words)
     - dynamic EQ (only where the recipe has one, currently techno)
     - glue compression
     - soft clip (off by default for ambient)
     - fade in and fade out (seconds)
   - **Short/Reel clip:**
     - length: 15 / 30 / 60 / 90 seconds
     - seamless loop: disabled when the file has no beat grid
     - drop override, set by dragging the drop marker on the waveform
   - **Video:**
     - style (genre default preselected)
     - emoji (radial style only), symmetry
     - title and artist
     - preview length, for a quick render first
   - **Show plan** button: runs `--plan-only --json` and shows the exact
     chain and steps before anything renders.
4. **Outputs, run, results.**
   - **Output checkboxes:**
     - Audio: master WAV 24-bit/48k, WAV 16-bit/44.1k dithered, FLAC, MP3 320
     - Clip: WAV
     - Video: YouTube 16:9, Short/Reel 9:16, Instagram 1:1
     - Text: captions, analysis JSON + PNG, REPORT
   - **Run:**
     - a progress view lists each step with a live percentage (video
       renders report frames done out of total)
     - an estimated time for video renders, plus a collapsible raw log
     - a Cancel button
   - **Results:**
     - audio players for the master and the clip, and video players for each render
     - the before/after mastering QC numbers
     - captions with a copy button
     - per-file download links, plus "download all" as a zip

A job list in a sidebar keeps earlier runs, so you can reopen a result
or re-run it with changed options without uploading again.

## Look and feel: modern CSS without a framework

- **Plain CSS** with custom properties for colors, spacing, radius, and
  type. No Tailwind or Bootstrap: one stylesheet of a few hundred lines,
  built into the binary.
- **Dark theme by default**, like a studio, with a light theme via
  `prefers-color-scheme` and a toggle. Accent colors come from the
  visualizer's gold-to-violet palette, so the app and the videos match.
- **Layout:** CSS grid for the screen layout, container queries so the
  options panels reflow, and `:has()` to style a card or panel based on
  its toggle state with little JS. It's responsive down to phone width.
- **Typography:** a system font stack, with tabular figures for BPM,
  LUFS, and times.
- **Motion:** subtle transitions on cards and toggles, turned off under
  `prefers-reduced-motion`.
- **Components:** genre cards, segmented controls (preset, clip length),
  switch toggles, range sliders with live values, a step progress list,
  and the waveform/section timeline (SVG drawn from the `peaks` array).
- **JavaScript:** vanilla ES modules, roughly 400 lines total: upload with
  progress (XHR), form state, an EventSource for progress, and waveform
  drag handles. No framework and no bundler.

## How it's built

```
process-audio/
  web/                       Go module (github.com/tomott12345/process-audio/web)
    cmd/paweb/main.go        flags, config, wiring, graceful shutdown
    internal/caps/           loads + caches pipeline_capabilities.py output (reloads when the recipes change)
    internal/upload/         streaming multipart -> disk, WAV header check, ffprobe
    internal/jobs/           job model, store (job.json on disk), worker queue
    internal/runner/         builds argv from validated options, exec, progress parser, cancel
    internal/httpapi/        routes, JSON handlers, SSE, file serving, zip
    ui/templates/*.html      html/template
    ui/static/{app.css,app.js}
  pipeline_capabilities.py   (Python side, built)
```

**HTTP API** (standard-library `net/http` with Go's built-in route
patterns, no router dependency):

| Method & path | Purpose |
|---|---|
| `GET /` | The app |
| `GET /api/capabilities` | Genres, options, defaults, which options apply, allowed ranges, output formats |
| `POST /api/uploads` | Streaming upload; returns `upload_id` + probe info |
| `POST /api/uploads/{id}/analyze` | `{genre}` → runs `music_analyze.py`, returns the analysis JSON |
| `POST /api/plan` | Options → `--plan-only --json` result |
| `POST /api/jobs` | Upload + genre + options + outputs → `job_id` |
| `GET /api/jobs` / `GET /api/jobs/{id}` | Job list, job state |
| `GET /api/jobs/{id}/events` | Live progress (server-sent events): step events + log lines |
| `POST /api/jobs/{id}/cancel` | Cancel |
| `GET /api/jobs/{id}/files/{name}` | Download one output (names checked against the job's own list of outputs) |
| `GET /api/jobs/{id}/zip` | Stream all outputs as a zip |
| `DELETE /api/jobs/{id}` | Remove a job and its files |

**Running jobs:**
- **Queue:** a worker pool with concurrency 1 by default (configurable).
  Video rendering keeps every core busy, and two at once would just
  thrash the CPU.
- **Running the scripts:** `exec.CommandContext` with an argument list,
  never a shell. Each option is checked against the capabilities
  (allowed values, numeric ranges) before it becomes a flag.
- **Cancel:** the child runs in its own process group (`Setpgid`), so
  Cancel kills the Python process *and* the ffmpeg/visualizer processes
  it started.
- **Job folders:** each job lives in `data/jobs/<random id>/`, holding
  `input.wav`, `job.json` (options, state, timings), the outputs, and
  `REPORT.txt`. On restart the job list is rebuilt from disk, and any job
  that was mid-run is marked "interrupted".
- **Cleanup:** jobs older than N days (default 14) are deleted, and a disk
  quota check runs before each upload.

**Uploads:**
- **Streaming:** files are streamed straight to disk with
  `http.MaxBytesReader`. The default limit is 2 GB: a 45-minute
  24-bit/48k stereo jam is about 780 MB.
- **Validation:** WAV only, checked by the RIFF/WAVE header, not the file
  extension.
- **File names:** the original name is kept only for display. The file on
  disk is always `input.wav`.

**Security** (it runs scripts on uploaded files, so this matters even
locally):
- listens on `127.0.0.1` unless `--listen` is given, and `--listen`
  requires `--token`, sent as a cookie after a login page
- CSRF protection on POST/DELETE (same-origin check plus a per-session token)
- random job IDs; downloads limited to each job's own list of outputs, so
  no path traversal
- no user text reaches a shell; title and artist go in as plain arguments
- `Content-Security-Policy` that allows only same-origin scripts and styles

## Build order

1. **Python additions:** `pipeline_capabilities.py`, the new
   `process_music_wav.py` flags and `--formats`, and `release.py --outputs`
   / `--progress-json` / `--plan-only --json`, plus `peaks` in the
   analysis. Each change keeps today's command-line behavior exactly.
   Checked with the synthetic test tracks from milestone 1 (moved into
   `tests/make_test_tracks.py`).
2. **Go backend:** server, capabilities, upload + probe, job store/queue,
   runner with the progress parser and cancel, SSE, downloads and zip.
   - Table-driven tests for options → argv, covering every genre, the
     edge cases, and rejected values.
   - An integration test that runs a real 3-second job on a synthetic WAV.
3. **Front end:** templates, `app.css`, and `app.js` for upload → genre
   cards → options from capabilities → run with live progress → results.
4. **Analysis-first features:** auto-analyze on genre pick; the waveform
   and section timeline; drag-to-trim and drag-the-drop-marker; options
   that depend on the file (no beat grid → no loop).
5. **Hardening and polish:**
   - the token login and CSRF protection for `--listen`
   - cleanup TTL and the disk quota
   - interrupted-job recovery and "re-run with changes"
   - `.claude/launch.json` so the app runs in the preview pane
   - a README section

Phases 1–3 give a working app end to end. Phases 4–5 are the parts that
make it pleasant and safe to leave running.

## Testing

- **Go:** unit tests for validation and building the argv (the riskiest
  code, since it's the boundary between web input and running a process),
  and for parsing the progress events and job state changes.
  `go test ./...`.
- **Python:** the milestone-1 synthetic tracks cover each new flag.
  Rendering with a step turned off, or a format added, still has to meet
  the same loudness and true-peak checks.
- **End to end:**
  - run the app in the preview browser and upload each synthetic genre
  - confirm options hide or disable correctly (ambient: no loop; dynamic
    EQ shown only for techno)
  - run with a 3-second video preview, then check the result players,
    downloads, and cancel mid-render
- **Layout:** desktop and phone widths, light and dark.

## Open questions

1. **Who uses it, and from where?** Only you on this Mac (localhost), or
   other devices on your network, such as a phone in the studio? This
   decides how much of the phase 5 security work is needed up front.
2. **Nature still-image videos:** the nature pipeline can mux still
   images into long/short MP4s. Supporting that needs an image upload as
   well as the WAV. Add it in the web app's first version, or later?
